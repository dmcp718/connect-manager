# Key Concepts

## Lazy loading

ExternalEntries are **metadata references**, not copies. No S3 data is transferred during import. When a user opens the file through LucidLink, the client streams the object directly from S3 using pre-signed URLs generated by the DataStore configuration.

## Path mapping

The mapping between S3 object paths and LucidLink filespace paths is **flexible and entirely up to the administrator**. There is no required structure — you can map S3 objects to any location in the filespace.

The examples in this guide use a convention that mirrors the S3 bucket and prefix hierarchy 1:1 into the filespace:

```
S3:        s3://my-bucket/photos/2025/image.jpg
Filespace: /my-bucket/photos/2025/image.jpg
```

But you could just as easily flatten, reorganize, or rename paths to fit your team's workflow:

```
S3:        s3://client-raw-assets/project-alpha/footage/clip001.mov
Filespace: /Projects/Alpha/footage/clip001.mov

S3:        s3://archive-2024/q3/reports/summary.pdf
Filespace: /Reports/2024-Q3-Summary.pdf
```

The `objectId` in the import payload is always the raw S3 key (e.g., `photos/2025/image.jpg`), while `path` is the filespace destination you choose — with a leading slash and whatever directory structure you define. The only requirement is that parent folders exist before importing files into them (see [Folder creation order](#folder-creation-order) below).

## Multiple links

It is possible to link an S3 object to multiple filespace entries at different paths in the same filespace, or even across multiple filespaces. This means importing the same object twice to the same path will create a duplicate entry — not return an error. Keep in mind that each link is billed as additional storage.

## Folder creation order

Folders must be created top-down (parent before child) because each folder creation requires the parent's entry ID. When importing many files across different directory trees, collect all unique directory paths, sort them, and create them sequentially before starting file imports.

## DataStore credentials

The IAM credentials provided when creating a DataStore are stored by the LucidLink service. These credentials generate pre-signed URLs when users access imported files. The IAM user needs at minimum:

| Permission | Purpose |
|---|---|
| `s3:GetObject` | Streaming file content to users |
| `s3:ListBucket` | Browsing bucket contents |

## Deleting a DataStore

```
DELETE /filespaces/{filespace_id}/external/data-stores/{datastore_id}
```

Returns `200`–`204` on success. Deleting a DataStore does **not** remove the ExternalEntries that reference it — those entries become inaccessible until the DataStore is re-created or entries are cleaned up.
